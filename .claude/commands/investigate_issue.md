description: Run the engineering team over a GitHub issue — plan, draft a fix, verify, security-review, and report back on the issue.
argument-hint: <issue number | crashlytics id | short description>
---

Investigate: **$ARGUMENTS**

Drive this through the engineering team. Do not skip stages, and do not collapse two stages
into one agent — the separation is what makes the verdicts trustworthy.

## 0. Load the item

If the argument is an issue number, read it with `mcp__github__issue_read` (method `get`,
plus `get_comments`). If it is a Crashlytics ID or a description, find the matching open
issue with `mcp__github__search_issues` before starting — if one exists, work that issue
rather than duplicating the analysis.

Carry the full stack trace, affected versions, and any signals (`SIGNAL_EARLY`) forward into
every stage. Agents cannot see the issue body unless you pass it.

## 1. Plan — `manager-engineer`

Returns a work breakdown: per unit a goal, expected files, owner, `verifiable_on_linux`,
dependencies, and a scope guard.

If the breakdown is a **diagnostics unit** (empty stack, no app frame, low confidence), stop
after this stage. Post the manager's recommendation as an issue comment and report back.
There is nothing to implement, and drafting a speculative patch is worse than saying so.

## 2. Implement — `implementation-engineer`

One agent per unit, with the unit's goal, files, scope guard, and the stack trace. Use
`isolation: "worktree"` for parallel units or anything touching more than a couple of files;
the `SessionStart` hook copies gitignored secrets into the worktree automatically.

## 3. Verify — `quality-engineer`

Runs on the resulting diff against the unit's stated goal. Returns PASS /
PASS (partial verification) / FAIL.

A **FAIL** goes back to `implementation-engineer` with the finding — never patched by the
quality engineer, never surfaced to me as finished. Loop until PASS, or until the finding
needs a scope decision, which goes back to `manager-engineer`.

**PASS (partial verification)** is the expected outcome for anything touching `iosMain` —
this is a Linux container and iOS targets are Kotlin/Native. Carry that caveat into the
issue comment verbatim. Never let it get rounded up to "verified".

## 4. Security review — `security-engineer`

Run whenever the diff touches secrets, `BuildConfig`, manifest permissions, consent/UMP or
ad loading, Crashlytics/Datadog/analytics payloads, RevenueCat or billing, notifications, or
deep links. When in doubt, run it — read-only and cheap.

Findings *in the diff* block the unit. Pre-existing observations go back to
`manager-engineer` as separate units; do not widen this change to absorb them.

## 5. Integrate — `manager-engineer`

Confirms: goal met, checks green or honestly caveated, security cleared, diff within scope,
Conventional Commit message valid.

## 6. Report on the issue

Post **one** consolidated comment via `mcp__github__add_comment_to_pending_review`'s issue
equivalent (`mcp__github__add_issue_comment`), containing:

- **Proposed fix** — the diff, in a fenced block
- **Verification** — what was run, what passed, and *explicitly* what could not be run here
- **Security** — verdict, or "not applicable"
- **Out of scope** — anything deliberately left, and where it was routed

End the comment with the attribution footer:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```

Then label the issue `investigated` (create the label if missing).

## Standing limits

- **Do not open a pull request** unless I explicitly ask in this session.
- Do not merge, close, or reopen anything.
- Do not push to `main`. Work on a branch named for the issue (`fix/issue-<n>-<slug>`).
- Never add Claude as a commit co-author.
- Comment **once** per investigation. If you have already commented on this issue with an
  investigation, update that comment's content in a new one only if something material
  changed — do not re-post the same analysis.
